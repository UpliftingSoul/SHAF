# SHAF 网站使用与测试指南

面向调试员：通过页面验证业务行为，必要时请维护人员核对数据库与日志。本指南覆盖十二个页面及未提供网页入口的核心模块；部署步骤见 [DEPLOY](DEPLOY.md)，日志/数据库操作见[运维手册](operations.md)。

## 1. 测试前准备

使用独立测试环境或明确允许写入测试记录的实例，保留提交号、模型配置、知识版本、测试时间。退款、工单、审核、评估会写库；语料生成和大评估消耗 API 配额。不要在有真实用户的环境停依赖或重置知识。

个人部署无需域名/HTTPS：通过 SSH 隧道或受来源 IP 限制的公网 IP 打开页面。1Panel 用于查看容器、日志和文件，不安装 OpenResty。首次公网 HTTP 访问用新浏览器/无痕窗口确认能创建身份并聊天，刷新后沿用该身份；换网址会形成不同的浏览器本地记录。

后文 `dc exec backend ...` 是服务器终端的备用入口，`dc` 定义见部署手册；也可在 **1Panel → backend → 终端（/bin/bash）**直接执行后面的 `make ...` 或 `uv run ...`，不要把 `dc` 写进容器终端。有网页作业按钮时优先点击；独立分类器启停由面板/Compose 处理。

首次最短顺序：聊天 → `/kb` 四路检索 → 工单/退款确认 → 飞轮审核 → Langfuse → 分类器。RAG 大评估、语料生成、训练放最后，串行执行。

| 页面 | 功能 |
|---|---|
| `/` | 客服对话、历史、引用、反馈、选单和业务表单 |
| `/admin` | 六个模块的状态聚合 |
| `/kb` | 材料、切块、入库、向量化、检索、历史对话挖掘审核 |
| `/review` | 知识缺口人工审核与写回 |
| `/rag-eval` | 检索/生成质量报告、编造个案处置 |
| `/observability` | 意图 Token、评估趋势、置信度校准 |
| `/topics` | 17 类主题分布 |
| `/topics/questions` | 主题问题列表与分页 |
| `/acceptance` | 分类器九项验收总览 |
| `/acceptance/eval` | 分类指标、红线、阈值、矩阵、单句实验 |
| `/acceptance/data` | 语料血缘、数据切分、模型与 ONNX 产物 |
| `/acceptance/errors` | 错例与边界配对复核 |

页面“缺产物”表示没有可读报告，“不达标”表示报告已生成但未过线，“错误/离线”表示取数或依赖失败。仓库已有报告不代表本次部署结果；先看报告时间及本次作业日志。退出码 0 也不一定过业务质量闸，需看报告字段。

## 2. 客服对话与业务流程 `/`

### 2.1 基本操作

输入问题，Enter 发送、Shift+Enter 换行，也可点击建议问题。回复应逐段显示；工具标签与引用视实际链路出现。点击“新对话”开始独立会话，左栏切换历史。

浏览器保存本地用户/会话标识，换浏览器、无痕模式、域名或端口可能产生不同身份；不是账号登录。历史回载当前只恢复用户/助手正文，不完整重建旧工具卡、引用和中断卡。页面 ONLINE 标识不是依赖健康证明。

### 2.2 核心场景

| 测试输入/步骤 | 应观察的行为 |
|---|---|
| “你好” | 闲聊回复，不创建业务工单 |
| “退货运费由谁承担？” | 知识问答先检索，有证据再回答，可查看引用 |
| “订单 1001 的物流到哪了？” | 查询订单取得物流单号，再走物流 MCP；工具轨迹与文字相符 |
| “订单 2002 什么状态？” | 查询当前用户订单，返回稳定 mock 数据 |
| “订单 1001 的商品还在保修期吗？” | 根据订单信息调用售后 MCP 保修查询 |
| “订单 1001 的退货进度怎么样？” | 售后退货状态工具可用；不误当新退款申请 |
| “我要投诉，猫砂盆质量有问题” | 投诉处理/建议动作，不承诺真实人工已接入 |
| “帮我写一段 Python 代码” | 超出客服范围时合理兜底 |
| “贵店能提供尚未公布的某项服务吗？” | 无知识证据时拒答/兜底，不能编造服务承诺；问题是否落池以来源与日志核对 |

工具选择受意图判断和模型影响；不要将固定措辞、每次所有工具标签都相同作为判据。九类意图是客服路由，与旁路 17 类主题分类不同。

### 2.3 退款：先选单，再明确提交

1. 新会话说“我要退款”，未提供订单时应出现订单选择或明确追问。
2. 选择订单，查看订单信息与政策处理，预期出现退款建议/表单。
3. 表单订单号只读；原因选“七天无理由 / 质量问题 / 发错货 / 不想要了 / 其他”。取消不应新增退款工单。
4. 确认提交后显示申请工单号；请维护人员查 `tickets`，应为退款类型，描述包含订单与选择原因。

退款是申请记录，不会调用真实支付打款。模型提出 `submit_refund` 不等于已经写库；以表单提交及 tickets 为准。

### 2.4 工单：描述、预览、确认/取消

1. 新会话说“帮我建个工单”：描述不足时先追问，不立即写单。
2. 补充“我的智能猫砂盆漏电，一开机就跳闸”：观察工单预览与确认交互。
3. 先选择取消，核对 tickets 未增加；另建测试会话再确认，核对新增一条并有工单号。
4. 维护人员核对 `tool_audit_logs` 的工具与状态。只读工具可重试，写工具不自动重试。

“转人工”是模拟交互，与实际创建工单是不同动作。重复请求不能当作可靠幂等机制，出现不确定结果先查库再提交。

### 2.5 多轮、历史与反馈

- 先问“查订单 1001”，再问“它到哪了”：指代应结合当前历史，不能串到另一个会话订单。
- 新开会话聊另一个订单，再切回来，核对两份正文历史独立。刷新后历史仍在，旧复杂卡片不会完整重放。
- 长对话后观察“已摘要”提示与关键事实保留；1M 窗口不保证短测试会触发摘要。维护人员可看 `conversation_summaries`；不要为强行触发而批量刷真实 API。
- 点 👍 只记录日志；点 👎 应将对应问题以 `user_feedback` 入池。较早答复可能没有召回快照，这是防止跨轮错配的正常行为。
- 模型/网络故障应显示错误，不把断流当完整成功。检查 SSE 帧；HTTP 200 不排除 `event: error`。

checkpoint 跨重启应保留，但刷新不会自动重建未完成中断卡。要验收重启续跑，维护人员记录 pending 会话号，在无作业时重启 backend，再通过 `/api/actions/resume` 按原中断提交 `order_id` 或 `confirmed`，核对原线程续跑；不要把新发一句消息当作同一暂停点恢复。

## 3. 知识库 `/kb`

### 3.1 初始盘点与四路检索

刷新库存，检查六份材料存在、MySQL 块数、pending/done、Milvus 在线、双写一致提示。用“邮费是多少”“猫砂盆 Pro 型号”分别选 vector、bm25、hybrid、hybrid_rerank，查看 Top-K 结果和来源小节。

vector 看语义近似；BM25 看词面命中；hybrid 用 RRF 融合；hybrid_rerank 再精排。各策略分数尺度不同，不横向直接比较数字大小。主键/正文/来源正确比固定排名更关键。

### 3.2 手工录入与幂等

用独立测试条目，例如 Markdown 标题“测试专区”，正文“测试专区售后回访时间为工作日 10:00–12:00”。选择内容类型、预览，检查标题路径、块正文、表格拆行、关键条款等提示，再确认入库。

选择立即向量化时验收检索能召回；关闭时应先 pending，点击向量化待补块后变 done。重复录入完全相同文本应跳过重复，不持续增块。编辑正文后要重新预览，不能提交旧预览。

向量化失败应显示错误及待补状态；依赖恢复后可重跑。`consistent=true` 是数量和状态检查，不等同于逐条内容校验。

### 3.3 离线材料与历史挖掘

初次离线建库、向量化按部署手册；已存在文档块时建库整体跳过。材料更新按运维手册补丁重嵌，新增小节用页面录入，不清库。

运行“对话挖知识”，查看抽取→去重→待审记录。仅 `kept` 可采纳/弃用；模型挖掘结果不会自动入正式知识。人工检查答案是否普遍有效、是否夹带订单号或个体信息。采纳成功后变 approved，知识可检索；弃用后变 rejected，不入库；重复操作应报告状态冲突。

“灌历史种子”“清库重建”是旧 Docker 入口，独立容器部署中不使用这些网页按钮。测试新知识的删除/隔离由维护人员处理，不能为清理一条记录重置全库。

## 4. 数据飞轮 `/review`

1. 在聊天中制造知识缺口，或对答复点踩，核对低置信问题入池。
2. 请维护人员执行 `dc exec backend make flywheel`；应用不会自动安装定时任务，网页无独立运行按钮。
3. `/review` 查看待审、通过、驳回及全部；核对标准化问题、出现频次、原始问题和召回快照。快照可能为空。
4. 相近问题经归并应累计 occurrence_count，失败问题留待重试。
5. 审核先排除垃圾、强时效、低价值条目。AI 示例答案只供参考，人工填写准确核准答案再通过。
6. 通过后写入知识并向量化，重新检索/问同类问题验证；驳回不入知识，同类后来再出现只累计次数，不自动恢复待审。

写回失败时先查报错和状态，再修依赖重试；并发冲突可能提示知识已写入但审核状态变化，应人工核对，不重复盲点。历史 QA 挖掘的 staging 与这里的 review_queue 是两个不同审核队列。

## 5. RAG 评估 `/rag-eval`

在知识库和三个云模型接口就绪后，运行“RAG 评估”；该作业耗时和费用较高。查看本次报告时间、样本量、四策略结果和可答桶分布。

| 指标 | 阅读方式 |
|---|---|
| Recall@K | 正确证据是否进入前 K 个召回结果 |
| MRR | 首个正确证据排得多靠前，越高通常越好 |
| 证据覆盖 | 是否召回回答所需条款/要点，不等同最终答案正确 |
| 忠实度 | 答复是否受给定证据支持，受裁判模型影响 |
| 拒答率 | 库外问题是否按约束拒答，应结合题目桶解读 |

生成段缺失时只有检索结果，不能宣称整轮通过。服务端支持 `make eval-rag SKIP_GEN=1` 只跑检索，但不是完整评估替代品。

编造个案区展开问题、答案、证据全集和裁判原因。真实问题修正后标“已解决”，裁判误判标“无需解决”，两者均填写依据；重新评估再次判出可自动回到未解决。处置按钮本身不修改知识。

“裁判判出率”与“人工确认幻觉率”按本轮实际参与评估题量计算；未人工过目的编造线索不全部计入确认值，因此确认值可能是下界。累计台账条数用于跨轮追踪，不拿它除以本轮题量。

## 6. 观测与成本 `/observability`

三个区块各自独立：

- **意图成本账**：先产生本次 Langfuse trace，再重跑；看按意图的 Token、请求数、平均值和占比。它不是货币账单。
- **评估趋势**：重跑评估流水线会在 eval_runs 插入新轮次。至少两轮才能合理比较变化；相同数据集/模型/知识版本下的对比更有意义。
- **置信度校准**：重跑扫描，比较推荐阈值与在用阈值；报告不会自动修改配置。由维护人员核准回填后重建后端。

不为让页面变绿盲目降低阈值。成本缺失不应连带让趋势区白屏，MySQL 故障也不应伪造零分。云端 trace 具体操作见运维手册。

## 7. 主题与分类验收

### 7.1 主题分布 `/topics`、问题列表

先有低置信问题，再在验收页运行旁路归类。默认攒够 10 条才跑；少量测试使用“不足一批强跑”。第二次在无新问题时运行应无新增记录，这是幂等边界。每轮最多 500 条。

主题共 17 类，一条问题可多标签，因此类目计数之和可大于已归类问题数。点击类目进入 `/topics/questions?label=...`，检查问题、标签、分页和返回；无数据时显示空态，非法类目为错误。归类不改变在线九类意图路由。

### 7.2 九项总览 `/acceptance`

| 验收项 | 关注的证据 |
|---|---|
| 语料与数据集 | 训练/验证/测试存在，文本重叠为 0 |
| 黄金样例闸 | 本次预标 prompt 通过率达到报告闸线 |
| 训练产物 | 权重、tokenizer、阈值存在，模式看 training_config.json |
| ONNX 与服务 | 本次导出标签一致、概率容差通过，服务在线 |
| 测试集评测 | 严档每类 F1≥0.9、中档≥0.8；宽档无硬线 |
| 阈值扫描 | 验证集九候选线、推荐值与模型阈值一致 |
| 混淆矩阵 | 17 类各自 TP/FP/FN/TN，重点看错误方向 |
| 错例复核 | 文本、真实标签、预测标签及矩阵账对应 |
| 旁路归类 | 本次批处理状态、写入量、主题数据 |

总览绿色不代表所有商业能力都验证：旁路空批次也可能显示通过，训练项主要检查文件存在。需结合本次日志、数据/模型版本及实际新增分类记录。旧网页分类器启停按钮不管理独立容器，由负责人用 Compose。

### 7.3 详细页面

`/acceptance/data`：查看捞池→清洗→预标/模拟补足→切分的血缘。训练集可增强，验证/测试不增强；按实际语料人工抽审，修正源 JSONL 后重新切分/训练。零文本重叠只排除字面泄漏，不保证语义完全无泄漏。

`/acceptance/eval`：micro 聚合所有标签判断，macro 平均各类表现，二者都要看；support 小的类更容易波动。单句实验输入“买大了想退”“快递到哪了”“买大了想退，快递还没到”等，查看多标签和各类得分。得分是 sigmoid 分类置信分，不是保证校准的概率；没有标签过阈值时当前服务回退最高分类。

`/acceptance/errors`：按错例和边界配对定位漏标、误标；一条错位预测可同时贡献 FP 和 FN，所以错例条数不等于矩阵错账数。修训练数据或提示词，冻结考题，重跑相关流水线。

训练顺序、LoRA 参数与发布回退见部署/运维手册；测试指南不重复安装步骤。

## 8. 未提供网页入口的模块与辅助回归

服务器项目根目录定义部署手册的 `dc` 简写后运行；先确认脚本前置条件。下表为较贴合当前架构的入口，不将所有历史脚本都当硬验收：

| 模块 | 命令与验证边界 |
|---|---|
| ch01 结构化售后提取 | `dc exec backend make eval`：调用 `/api/extract`，无需专门网页 |
| ch03 切块/检索/挖掘 | 网页 + `make eval-retrieval` / `make eval-mining`；需知识库/模型 |
| ch04 RAG | `dc exec backend make eval-check`，再 `make eval-rag`；需 Milvus 和云模型 |
| ch05 图编排 | `dc exec backend make eval-ch05`；检查工具轨迹及停止行为 |
| ch06 意图/指代/续跑 | `dc exec backend uv run --no-sync python -m scripts.eval_intent`、`python -m scripts.eval_coref`（同 uv 前缀）；网页退款/选单配合核对 |
| ch07 摘要 | `dc exec backend make eval-ch07` 主要测摘要事实保留/无编造；分层滑窗还需长对话及受控测试 |
| ch08 MCP/工具 | `dc exec backend make eval-ch08` 会创建测试工单、审计并验证取消；先确认允许写数据 |
| ch09 飞轮/趋势/校准 | `make flywheel` / `make eval-flywheel` / `make calibrate-confidence`；配合审核页 |
| ch10 分类 | 数据→训练→评测→导出→服务→扫描→归类，按第 7 节验收 |

表中省略 `dc exec backend` 的 make 命令仍在后端容器运行。HTTP 评估脚本多数硬编码 localhost:8000，需 `exec backend`，不能直接在宿主执行。旧 eval-agent/eval-ch06 等部分断言沿用更早工具名称/流程，失败先与当前接口核对；不以旧脚本误报推翻正常的新链路。`smoke_milvus_bm25.py` 硬编码 localhost:19530，不能直接在后端容器运行；生产验证用 `/kb` 四路检索。

单独测试结构化提取可在服务器访问同域接口：

```bash
curl -fsS http://127.0.0.1:8080/api/extract -H 'Content-Type: application/json' \
  --data '{"text":"订单1001的猫爬架少一根立柱，我想申请补发"}'
```

应返回符合 schema 的 JSON，而非自然语言；字段定义见后端 OpenAPI 或 `app/schemas/extract.py`。Nginx 默认不开放后端 `/docs`，需要接口文档时由维护人员提供受控入口。

**不要在业务实例直接运行完整 pytest**：数据库夹具会删除并重建测试库表。专用测试库、测试凭据及独立 Milvus 测试集合先配置；TEST_DATABASE_URL 绝不能指向业务库。生产镜像不含 dev 组和全部测试源码，受控单元测试在开发环境/专用测试镜像执行。

## 9. 测试记录与通过判定

每个案例记录：提交号、模型/API、知识版本、页面/输入、时间、会话/作业号、预期、实际、日志或报告路径。状态使用“通过 / 失败 / 环境缺失跳过”，不把跳过计入通过。

验收既看页面反馈，也看数据库/产物。首次重点检查前后端链路、中断确认、知识双写、MCP、云 trace 与分类写库；模型质量分数单独记录，不与页面功能正确混为一个结论。
